## Hard constraint: replicate, never import

**The node must not depend on `@pipelex/sdk` in any way — not as a runtime dependency, not as a devDependency, not in a test.** `PipelexApiShapes.ts` is a hand-maintained replication and stays that way.

That closes Open Question 1 below (the "bundle instead of vendor?" spike): **don't**. It also rules out the type-level conformance test an earlier draft of this plan proposed — a first pass at Phase 0 did add `@pipelex/sdk` as a types-only devDependency, and it was removed. Replication is the standing decision, so its consequence has to be stated honestly rather than papered over:

**Nothing in this repo can automatically detect that the SDK changed.** No import means no programmatic comparison. What replaces it is deliberately modest:

- `test/WireContract.test.ts` pins the contract the node *believes in* — exact snake_case field names, the full result-field set it reads, the status → meaning mapping. It catches an accidental edit and the silent-typo class of bug (`dynamic_output_concept_code`, which the runner discarded without error). It **cannot** catch an SDK-side addition.
- `PipelexApiShapes.ts` carries the re-sync procedure and a version stamp: which `pipelex-sdk-js` files to diff, what to bump, which pins to update.
- Catching SDK-side change therefore stays a **human** step. The realistic hook is the release process: when `pipelex-sdk-js` cuts a version touching `src/runs.ts` or `src/client.ts`, someone re-reads this file. Worth deciding whether that belongs on the SDK's own release checklist — this repo cannot see it, which is exactly how ten releases went by unnoticed.

## Original findings (kept as the record; items marked ✅ above are done)

## Why this exists

The n8n node cannot import an SDK. `@n8n/scan-community-package` rejects any `dependencies` entry, so `nodes/Pipelex/MthdsShapes.ts` **copy-pastes** the wire shapes it needs. That is a correct decision and this plan does not change it — but a copy has to be re-synced deliberately, and it has not been.

Two things happened since the copy was taken:

1. **The copy source moved repos.** `MthdsShapes.ts` says it was copied from **mthds-js v0.10.0** and names `mthds-js/src/client/pipeline.ts`, `runs.ts`, `client.ts` as the files to sync against. The durable run lifecycle has since left `mthds-js` (now protocol-only) and lives in **`pipelex-sdk-js`** — `src/runs.ts` and `src/client.ts`. Every sync pointer in that header is dead.
2. **The lifecycle kept evolving.** The node's `v0.1.0` shipped 2026-06-12. `pipelex-sdk-js` `v0.1.0` shipped 2026-06-27 and is now at **v0.10.0** — ten releases of run-lifecycle work the node never tracked.

The good news, established by reading the code: because the node spreads the response body (`{ ...outcome.body }`), **additive server fields already reach the n8n item**. So the drift is mostly *types, docs, error wording, and missing capability* — not silent data loss. There is one real user-visible bug (§D) and one real capability hole (§E).

Ground truth used throughout, in preference order: the server (`pipelex-server/platform/src/pipelex_platform/routers/v1/{runs,execution}.py`), then `pipelex-sdk-js/src/`, then the node.

## Findings

### A. The provenance header is wrong

`MthdsShapes.ts:1-15` points at three `mthds-js` files that no longer own the lifecycle. Anyone following those pointers syncs against the wrong contract.

**Fix:** repoint to `pipelex-sdk-js/src/runs.ts` (`RunStatus`, `RunResults`, `RunResultState`, the poll semantics), `pipelex-sdk-js/src/client.ts` (`start`, `getRunStatus`, `getRunResult`), and `mthds/protocol` (`RunRequest` / `StartRequest` / `RunResultStart`, which is all `mthds-js` still owns here). Record the SDK version the copy was taken from, as the header already does.

### B. `RunResults` is missing `tokens_usages` and `usage_assembly_error`

The server returns both (`runs.py:101-127`, `RunResultsResponse`), and the SDK types both (`runs.ts:158-189`, plus the whole `TokensUsageRecord` shape — per-call token counts by category, model id, the pipe that made the call, and a computed **USD `cost`**).

The node's vendored `RunResults` (`MthdsShapes.ts:75-86`) knows neither. They still reach the item via the spread, so this is not data loss — but it is an **undocumented feature**: per-run cost and token attribution is exactly what an n8n user wants to branch on, aggregate, or push to a spreadsheet, and today nothing tells them it is there.

Note the traps the SDK documents and the node would need to carry: the categories in `nb_tokens_by_category` are **not additive** (`input` already includes `input_cached`; summing double-counts), `cost: null` means "no rate table" while `cost: 0` means "priced at zero", and there is **no run-level aggregate** — sum the records. `tokens_usages: null` is three-ways ambiguous (off / broke / pre-artifact run) and only `usage_assembly_error` separates them.

**Fix:** add both fields to the vendored type with the semantics above, and document them in `docs/usage.md`.

### C. The `main_stuff` invariant is not enforced

SDK `runs.ts:158` makes `main_stuff` **required** on a completed run (the pipelex ≥0.37 invariant) and `client.ts` throws `MissingMainStuffError` when a 200 arrives without it. The node types it `main_stuff?: unknown` and emits the item regardless — so a degraded 200 becomes `{ status: "COMPLETED" }` with no output and **no signal that anything is wrong**. Downstream nodes then fail on a missing field, far from the cause.

**Fix:** mirror the invariant. A 200 with `main_stuff == null` is an actionable error naming the run id, not a completed item.

### D. The 403 message is factually wrong — user-visible bug

`GenericFunctions.ts:21-22` tells the user their key "lacks runs access" and needs to be "admin / `runs:execute`-scoped".

There is **no `runs:execute` scope in the platform.** The gate that actually produces the 403 is `require_surface_access()` (`platform/src/pipelex_platform/deps.py:345-367`): an API-key-authenticated request needs the **`ff_api_keys` feature flag** on the account. The server's own message says so. A user reading the node's message goes hunting for a key scope that does not exist.

**Fix:** reword to name the real cause (the account's API-key access is not enabled — contact Pipelex / check the account), and prefer the server's `problem+json` `detail` when present, since it is already accurate. This is the one item worth shipping on its own.

### E. `files` / `bundle_b64` are missing — a method with custom Python is unrunnable from n8n

SDK v0.7.0 added **method-bundle transport**: a run can carry the whole method — the `.mthds` plus its `funcs/*.py`, `structures/*.py`, and `requirements.txt` — as either `files` (a `{ relativePath: text }` map) or `bundle_b64` (the same as a base64 zip). The server accepts both on `POST /v1/start` (`HostedStartRequest` / `HostedRunRequest`), and resolves a stored method carrying custom Python into an assembled bundle.

The node offers only `pipe_code` / `mthds_contents` / `method_id`. So **any method with a custom PipeFunc is not runnable from n8n at all** — the largest capability gap in this list.

It also means the node's local run-source validation is behind the standard: exclusivity is now normative (`assertExclusiveRunSources` in `mthds/protocol`) — a bundle is self-contained, so `files` XOR `bundle_b64` XOR non-empty `mthds_contents`, keyed on **presence** not emptiness, while the "something to run" precondition keys on **runnability** (an empty encoding carries no method).

### F. `GET /v1/runs/{id}/status` is never used

The route exists (`runs.py:303`) and the SDK wraps it (`getRunStatus` → `RunRead` = status + `degraded` + `retry_after_seconds`). The node never calls it.

So from n8n, "did it finish?" costs a **full results fetch** — which pulls `graphspec.json`, `main_stuff.json`, `working_memory.json` and `tokens_usages.json` from S3 in parallel, and then the node throws `graph_spec` away. For the scheduled-collector pattern the node's own docs recommend, that is the wrong primitive.

### G. Run history is entirely absent

`GET /v1/runs` (paged: `createdFrom` / `createdTo` / `limit` / `cursor`, newest first, `{items, nextCursor}`) and `GET /v1/runs/{id}` (`RunDetail`, including `mthds_contents` — the only record of what actually executed). Both new in SDK v0.10.0. Nothing in the node.

The v0.10.0 trap to carry: `createdFrom`/`createdTo` are **instants, not days** — ISO-8601 with a UTC offset. A bare `YYYY-MM-DD` or a naive timestamp is a **400**. The node must convert its own day boundaries; it cannot pass a date picker's value through.

### H. No way to feed an n8n binary into a method

n8n items carry **binary data** natively — that is how every file moves through an n8n workflow. Today a Pipelex method that takes a PDF or an image can only be run from n8n if the file already sits at a public URL.

The SDK closes this: `uploadFile` (accepts `Blob` / `ArrayBuffer` / `Uint8Array`) → a `pipelex-storage://` reference, and `prepareInputs` which resolves the pipe's declared inputs via the explicit inputs template, uploads the file-bearing values, and hands back rewritten inputs. For n8n specifically this is the highest-value item on the list — it turns "call an API" into "wire your existing file flow into a method".

### I. `Method ID` is free text; `listMethods` exists

The user hand-copies a `mt_...` id today. `GET /v1/methods` exists and the SDK wraps it. n8n's `loadOptions` gives a searchable dropdown for near-zero cost.

### J. `RunState` is typed as a closed union over an open server string

`MthdsShapes.ts:21` declares six values and calls it "the MTHDS Protocol `RunState` enum". The protocol defines no such enum any more — `RunResultStart` is `{ pipeline_run_id }` plus extensions, and `state` is a **hosted extension** typed `str` server-side (`StartAck`, `execution.py:215-225`). A closed union over an open string is a drift hazard for no benefit.

(`StartAck`'s `{ pipeline_run_id, state, created_at }` is otherwise correct — the server does return all three. Only the *provenance claim* and the closedness are wrong.)

### K. Poll-loop divergences — deliberate, but undocumented

| | SDK | node |
|---|---|---|
| base interval | 2s, raised by `Retry-After` | none; pure `Retry-After` (5s default) |
| timeout | 20 min (`DEFAULT_WAIT_TIMEOUT_MS`) | 300s `Max Wait`, `0` = unbounded |
| on timeout | throws `RunTimeoutError` | returns a usable "still running" item |
| sustained 503 | no ceiling | `MAX_CONSECUTIVE_DEGRADED = 5` |

All four differences are **right for n8n** (Cloud execution caps; an item beats an exception in a workflow). They should be stated as intentional divergence in the vendored header, so a future sync does not "fix" them into the SDK's numbers.

### L. Not in scope: the `Piplex` typo

`credentials/PiplexApi.credentials.ts`, credential name `piplexApi`, is baked into the published `0.1.0` manifest. Renaming it breaks every existing install's saved credential. Leave it; noted here so it is a decision rather than an oversight.

## The plan

### Phase 0 — Make drift visible (do this first) — ✅ done

Without this, everything below rots again. Constrained by "replicate, never import" above — see that section for what this can and cannot achieve.

- Repoint the shapes header at `pipelex-sdk-js` (§A), stamp the version replicated from, and write the manual re-sync procedure into it.
- Pin the wire contract at runtime (`test/WireContract.test.ts`): exact field names, result-field set, status → meaning mapping. Makes an edit to the replicated shapes fail loudly instead of drifting.
- State the deliberate poll-loop divergences (§K) in that header, so a future sync does not "fix" them into the SDK's numbers.
- Typecheck the test suite for real (`pnpm run typecheck:test`) — Vitest's esbuild strips types without checking them, so the suite was previously not type-checked at all.
- **Not** a types-only devDependency on `@pipelex/sdk`. Tried, removed; see the constraint section.

Deliverable: CI fails on the next contract move. No runtime change, nothing ships to users.

### Phase 1 — Correctness (small, shippable on its own)

- §D — fix the 403 message; prefer the server's `problem+json` `detail`.
- §C — enforce the `main_stuff` invariant with an actionable error.
- §J — widen `RunState` to an open string, drop the false protocol-enum claim.
- §B — add `tokens_usages` / `usage_assembly_error` to the vendored type and document them (including the non-additive-categories and `null`-vs-`0` traps) in `docs/usage.md`.

Deliverable: a patch release. One real bug fixed, cost/usage data documented for the first time.

> **Checkpoint.** Phases 0–1 land as one release: the node is now *honest and guarded* without any new surface. Re-read the plan here — everything below adds operations and UI, and is worth re-prioritising against whatever n8n users are actually asking for by then.

### Phase 2 — Close the run-source hole (§E)

- Add `files` and `bundle_b64` to the start body and to the node's UI. `files` wants a key/value collection (relative path → content); `bundle_b64` a single string, most plausibly fed from an n8n binary (which pairs with Phase 4).
- Port the exclusivity + runnability rules from `mthds/protocol` rather than re-deriving them, so the node rejects exactly what the server rejects, with an item-scoped error.
- Tests for each accepted and each rejected combination.

Deliverable: methods with custom PipeFunc Python become runnable from n8n.

### Phase 3 — The read operations (§F, §G)

- **Get Run Status** — `GET /v1/runs/{id}/status`. The cheap primitive for the scheduled-collector pattern. Surface `degraded` so a workflow can tell "still running" from "we could not reach Temporal".
- **List Runs** — `GET /v1/runs` with n8n's standard `returnAll` / `limit` pagination over `nextCursor`. Convert date inputs to **offset-bearing instants** (§G) — a naive value is a 400, so the node must not pass a picker value through.
- **Get Run Detail** — `GET /v1/runs/{id}`, including `mthds_contents` (what actually ran).

Operation count goes 4 → 7. Worth reviewing whether the flat dropdown still reads well, or whether a Resource split (Run vs Method) is now warranted — the node dropped Resource selectors back in `0.0.7` when there was one option; that reasoning expires here.

> **Checkpoint.** The node now covers the whole run lifecycle. Phase 4 is a different kind of work — it touches n8n's binary system and adds a second network round-trip before the run — so re-scope it deliberately.

### Phase 4 — Binary inputs (§H)

The highest-value item, and the most work.

- **Upload** an n8n binary property to `pipelex-storage://`, either as a standalone operation or as a mode on the start operations.
- Optionally port `prepareInputs`: resolve the pipe's declared inputs via `POST /v1/build/inputs` (`explicit: true`), rewrite the file-bearing values, then start. This is a real chunk of logic to vendor — port it only if the standalone upload proves insufficient in practice.
- Decide where the upload happens relative to the start call, and what a failed upload does to the item.

Deliverable: an n8n file flow can feed a Pipelex method directly.

### Phase 5 — UX and agent surface (§I)

- `Method ID` → a `loadOptions` dropdown backed by `GET /v1/methods`, with free-text still allowed (expressions must keep working).
- Consider a **Validate** operation (`POST /v1/validate`) — cheap to add, and genuinely useful to the AI-Agent path the node already advertises via `usableAsTool: true`: an agent can check a method before spending a run on it. Remember the contract rule: an invalid bundle is a **200** discriminated on `is_valid`, never an error — so it must be an item, not a thrown `NodeApiError`.

## Open questions

1. ~~**Bundle instead of vendor?**~~ **Closed: no.** Replicate, never import — see the constraint section above. The node stays self-contained with zero dependency on `@pipelex/sdk` of any kind, and Phase 4's `prepareInputs` work must be replicated too, however large.
2. **Operation count.** At 7–9 operations, does the flat dropdown hold, or does the node want Resource (Run / Method) back? Decide at the Phase 3 checkpoint, not before.
3. **Does the `/v1/version` handshake earn its round-trip here?** The node deliberately skips it and folds the bare-runner case into its 404 message. That is still defensible; revisit only if users actually point the credential at a self-hosted runner.
